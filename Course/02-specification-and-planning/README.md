# Урок 2. Техническое задание и план реализации

![Разбираемся с требованиями](https://media1.tenor.com/m/jBHd28HW1zwAAAAd/explain-confusion.gif)

## Назначение урока

На втором этапе мы превращаем идею `TaskerAI` в понятную инженерную задачу. После первого урока у нас уже есть агентная среда opencode: правила, агенты, навыки и ограничения. Теперь фиксируем документы, по которым агент сможет писать код без догадок и хаотичных решений.

В этом уроке мы создаем три рабочих артефакта:

- `PROJECT_SPEC.md` - техническое задание продукта;
- `IMPLEMENTATION_PLAN.md` - план реализации MVP;
- `ACCEPTANCE_CRITERIA.md` - критерии приемки результата.

Код на этом этапе еще не пишем. Наша задача - договориться о продукте, границах MVP, техническом стеке, рисках и порядке разработки, чтобы в третьем уроке агент не додумывал важные решения на ходу.

## Результат урока

К концу урока в рабочем проекте должна появиться такая структура:

```text
project-root/
  AGENTS.md
  TOOLS.md
  PROJECT_SPEC.md
  IMPLEMENTATION_PLAN.md
  ACCEPTANCE_CRITERIA.md
  opencode.json
  .opencode/
    agents/
    skills/
```

В `Course/02-specification-and-planning/ASSETS` лежат готовые примеры документов. Их удобно использовать как эталон, но для тренировки лучше сначала попросить агента задать вопросы, а уже потом собрать документы под конкретную группу или проект.

## Шаг 1. Проверить готовность после первого урока

Откройте рабочий проект, в который на первом уроке были скопированы файлы агентной среды.

Минимально должны быть готовы:

- `AGENTS.md`;
- `TOOLS.md`;
- `opencode.json`;
- `.opencode/agents/product-analyst.md`;
- `.opencode/agents/architect.md`;
- `.opencode/skills/product-spec/SKILL.md`;
- `.opencode/skills/implementation-plan/SKILL.md`;
- `.opencode/skills/quality-gate/SKILL.md`.

Проверочный промпт:

```text
Прочитай AGENTS.md, TOOLS.md и список доступных агентов/skills. Ничего не меняй. Кратко скажи, готов ли проект к подготовке технического задания, и перечисли, каких файлов или правил не хватает.
```

Если агент сообщает, что не хватает ключевых файлов первого урока, сначала восстановите агентную среду.

## Шаг 2. Задать рамку продукта

Перед генерацией ТЗ явно задаем рамку продукта. Для курса используем такое описание:

```text
Мы делаем веб-приложение TaskerAI.
Пользователь должен создавать задачи, редактировать их, менять статусы, фильтровать список и использовать ИИ-помощника для генерации задач, разбиения большой задачи на вложенные подзадачи и улучшения формулировки.
```

Важно зафиксировать ограничения:

- приложение должно быть достаточно простым для разработки в рамках курса;
- стек должен быть понятным и воспроизводимым;
- секреты AI API не должны попадать в код;
- базовые backend-автотесты и frontend-автотесты нужны уже на третьем уроке;
- Playwright, E2E и Docker будут доведены на четвертом уроке;
- второй урок не должен создавать `frontend`, `backend`, базу данных или Docker-файлы.

## Шаг 3. Попросить агента задать уточняющие вопросы

Если требования неполные, агент не должен сразу писать ТЗ. Сначала просим его найти недостающие решения.

Промпт:

```text
Используй роль product-analyst и при необходимости skill product-spec.

Нужно подготовить техническое задание для приложения TaskerAI.
Код не создавай.
Структуру frontend/backend не создавай.

Сначала задай до 10 уточняющих вопросов, которые нужны для качественного PROJECT_SPEC.md.
Сгруппируй вопросы по темам: пользователи, MVP, AI-функции, данные, ограничения, критерии готовности.
И предложи пару вариантов ответа на каждый с нумерацией, либо указать свой,  задавай вопросы в синтаксисе opencode
```

Для учебного курса можно принять такие ответы:

- пользователь один, без регистрации;
- хранение данных локальное через backend и SQLite;
- frontend на React + TypeScript + Vite;
- backend на Python + FastAPI;
- AI API подключается через переменную окружения, но в тестах мокируется;
- базовые backend-автотесты добавляются через pytest;
- базовые frontend-автотесты добавляются через Vitest и Testing Library;
- MVP должен запускаться локально;
- Playwright и Docker добавляются на четвертом уроке, но архитектура не должна этому мешать.

## Шаг 4. Создать `PROJECT_SPEC.md`

После ответов на вопросы попросите агента оформить техническое задание.

Промпт:

```text
Используй skill product-spec.

На основе ответов подготовь файл PROJECT_SPEC.md для приложения TaskerAI.

Файл должен содержать:
1. цель продукта;
2. границы MVP;
3. целевых пользователей;
4. пользовательские сценарии;
5. функциональные требования;
6. нефункциональные требования;
7. модель данных на уровне сущностей;
8. API на уровне endpoint-ов без реализации;
9. AI-функции;
10. технический стек;
11. ограничения и исключения из MVP;
12. риски и открытые вопросы.

Код приложения не создавай.
Создай только PROJECT_SPEC.md.
```

После генерации перечитайте документ как заказчик. Если в ТЗ есть спорные решения, исправьте их до планирования.

## Шаг 5. Проверить качество ТЗ

Попросите агента провести ревью документа перед созданием плана.

Промпт:

```text
Проведи ревью PROJECT_SPEC.md как архитектор и product analyst.
Ничего не меняй без отдельного разрешения.

Проверь:
1. нет ли противоречий;
2. понятно ли, что входит в MVP;
3. нет ли слишком больших требований для учебного проекта;
4. хватает ли данных для backend и frontend;
5. понятно ли, как проверять AI-функции без реальных затрат на API.

Верни список замечаний по приоритету: critical, important, minor. С возможностью подтверждения\отклонения (своего варианта) каждого - используй инструмент question в opencode
```

Если замечания есть, внесите минимальные правки в `PROJECT_SPEC.md` и повторите проверку.

## Шаг 6. Создать `IMPLEMENTATION_PLAN.md`

План реализации должен быть достаточно подробным, чтобы на третьем уроке можно было выдавать агенту небольшие задачи для его реализации.

Промпт:

```text
Используй роль architect и skill implementation-plan.

На основе PROJECT_SPEC.md подготовь IMPLEMENTATION_PLAN.md.

План должен быть поэтапным и включать:
1. целевую структуру проекта;
2. порядок реализации backend;
3. порядок реализации frontend;
4. порядок добавления AI-интеграции;
5. порядок добавления базовых backend-автотестов через pytest;
6. порядок добавления базовых frontend-автотестов без Playwright;
7. минимальные проверки после каждого этапа;
8. зависимости между этапами;
9. риски и способы снижения рисков;

Код не создавай.
Создай только IMPLEMENTATION_PLAN.md.
```

Хороший план - это не один большой пункт "сделать приложение". Он разбивает работу на маленькие шаги, которые можно проверить по отдельности.

## Шаг 7. Создать `ACCEPTANCE_CRITERIA.md`

Критерии приемки нужны, чтобы на третьем и четвертом уроках можно было объективно понять, готов ли MVP.

Промпт:

```text
Используй PROJECT_SPEC.md и IMPLEMENTATION_PLAN.md.

Создай ACCEPTANCE_CRITERIA.md для MVP приложения TaskerAI.

Файл должен содержать:
1. Definition of Done для MVP;
2. пользовательские сценарии приемки;
3. API-критерии;
4. frontend-критерии;
5. AI-критерии;
6. критерии ошибок и пустых состояний;
7. минимальные проверки перед финальным ответом агента;
8. что явно не считается обязательным на этом этапе.

Код не создавай.
Создай только ACCEPTANCE_CRITERIA.md.
```

## Шаг 8. Сверить документы между собой

В конце урока сверяем документы между собой. Это короткая остановка перед кодом: лучше поймать расхождения сейчас, чем чинить их уже в frontend и backend.

Промпт:

```text
Проверь связку PROJECT_SPEC.md, IMPLEMENTATION_PLAN.md и ACCEPTANCE_CRITERIA.md.
Ничего не меняй.

Найди:
1. требования из PROJECT_SPEC.md, которых нет в плане;
2. пункты плана, которых нет в PROJECT_SPEC.md;
3. критерии приемки, которые невозможно проверить;
4. слишком большие задачи для одного шага разработки;

Верни краткий отчет и предложи минимальные правки в виде вопросов с вариантами ответа через инструмент question в opencode, если такие правки есть.
```

После этого можно разрешить агенту внести точечные изменения.

## Шаг 9. Скопировать готовые ASSETS при необходимости

Если нужно быстро получить эталонные документы, скопируйте файлы из `ASSETS` в рабочий проект.

Пример для PowerShell из корня курса:

```powershell
Copy-Item -Force .\Course\02-specification-and-planning\ASSETS\PROJECT_SPEC.md .\TaskerAI\
Copy-Item -Force .\Course\02-specification-and-planning\ASSETS\IMPLEMENTATION_PLAN.md .\TaskerAI\
Copy-Item -Force .\Course\02-specification-and-planning\ASSETS\ACCEPTANCE_CRITERIA.md .\TaskerAI\
```

Пример для Linux/macOS из корня курса:

```bash
cp ./Course/02-specification-and-planning/ASSETS/PROJECT_SPEC.md ./TaskerAI/
cp ./Course/02-specification-and-planning/ASSETS/IMPLEMENTATION_PLAN.md ./TaskerAI/
cp ./Course/02-specification-and-planning/ASSETS/ACCEPTANCE_CRITERIA.md ./TaskerAI/
```

Если вы проходите урок интерактивно, лучше не копировать файлы сразу, а сначала сгенерировать свои версии через агента и сравнить их с эталоном.

## Критерии готовности урока

Урок можно считать закрытым, если на все пункты ниже получается ответить "да":

- в проекте есть `PROJECT_SPEC.md`;
- в проекте есть `IMPLEMENTATION_PLAN.md`;
- в проекте есть `ACCEPTANCE_CRITERIA.md`;
- в ТЗ явно описаны MVP, пользователи, сценарии, требования, ограничения и стек;
- AI-функции описаны без хранения секретов в коде;
- план реализации разбит на маленькие проверяемые этапы;
- в плане есть базовые backend-автотесты и frontend-автотесты для третьего урока;
- критерии приемки можно проверить вручную или автотестами;
- документы не требуют начинать с Playwright, Docker, E2E или сложной авторизации;
- агент подтвердил, что документы согласованы между собой;
- код приложения на этом уроке не создавался.
