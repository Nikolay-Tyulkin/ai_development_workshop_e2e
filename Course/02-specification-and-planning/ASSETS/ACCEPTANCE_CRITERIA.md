# ACCEPTANCE_CRITERIA: Менеджер задач с ИИ

## 1. Definition of Done для MVP

MVP считается готовым, если:

- пользователь может создать, увидеть, изменить и удалить задачу через интерфейс;
- задачи сохраняются через backend и не исчезают после перезагрузки страницы;
- пользователь может менять статус задачи между `todo`, `in_progress` и `done`;
- пользователь может фильтровать задачи по статусу и приоритету;
- пользователь может искать задачи по названию и описанию;
- AI-функции доступны через backend endpoint-ы;
- AI API key не находится во frontend и не хранится в коде;
- при отсутствии реального AI key работает мок-режим или понятный fallback;
- frontend показывает loading, error и empty states;
- frontend соответствует UI/UX-правилам;
- backend возвращает корректные HTTP-статусы;
- базовые frontend-автотесты проверяют ключевые UI-состояния без реального backend;
- проект запускается локально по инструкции;
- известные ограничения описаны в документации.

## 2. Пользовательские сценарии приемки

### Сценарий 1. Создание задачи

Дано: пользователь открыл приложение.

Когда: пользователь вводит название, описание, приоритет и дедлайн, затем сохраняет задачу.

Тогда: новая задача появляется в списке со статусом `todo`.

Критерии:

- задача отображается без перезагрузки страницы;
- после обновления страницы задача остается в списке;
- пустой `title` не сохраняется.

### Сценарий 2. Редактирование задачи

Дано: в списке есть задача.

Когда: пользователь меняет название, описание, статус или приоритет.

Тогда: изменения сохраняются и отображаются в списке.

Критерии:

- `updated_at` обновляется на backend;
- статус принимает только допустимые значения;
- при ошибке сохранения пользователь видит сообщение.

### Сценарий 3. Удаление задачи

Дано: в списке есть задача.

Когда: пользователь удаляет задачу.

Тогда: задача исчезает из списка и больше не возвращается из API.

Критерии:

- повторный запрос одной задачи возвращает `404`;
- удаление неизвестной задачи возвращает корректную ошибку;
- UI не оставляет удаленную задачу в состоянии редактирования.

### Сценарий 4. Фильтрация и поиск

Дано: в приложении есть задачи с разными статусами и приоритетами.

Когда: пользователь выбирает фильтр и вводит поисковую строку.

Тогда: список показывает только подходящие задачи.

Критерии:

- фильтр по статусу работает отдельно;
- фильтр по приоритету работает отдельно;
- поиск работает по названию и описанию;
- фильтры и поиск работают вместе;
- пустой результат показывает empty state.

### Сценарий 5. Генерация задач через AI

Дано: пользователь хочет разбить цель на задачи.

Когда: пользователь вводит цель и запускает генерацию.

Тогда: приложение показывает список предложенных задач.

Критерии:

- пользователь может выбрать, какие предложения добавить;
- добавленные предложения становятся обычными задачами;
- при ошибке AI пользователь видит понятное сообщение;
- без AI key доступен мок-ответ или fallback.

### Сценарий 6. Разбиение задачи на подзадачи

Дано: в приложении есть крупная задача.

Когда: пользователь просит AI разбить ее на подзадачи.

Тогда: приложение показывает список подзадач-кандидатов.

Критерии:

- предложения не сохраняются автоматически без действия пользователя;
- выбранные подзадачи добавляются как обычные задачи;
- исходная задача не теряется и не перезаписывается без подтверждения.

### Сценарий 7. Улучшение формулировки

Дано: пользователь пишет черновое название или описание задачи.

Когда: пользователь запускает улучшение формулировки.

Тогда: приложение предлагает улучшенный текст.

Критерии:

- пользователь может принять или отклонить предложение;
- исходный текст не заменяется без подтверждения;
- ошибка AI не блокирует ручное сохранение задачи.

## 3. API-критерии

### Tasks API

- `GET /api/tasks` возвращает список задач.
- `GET /api/tasks?status=todo` возвращает только задачи со статусом `todo`.
- `GET /api/tasks?priority=high` возвращает только задачи с высоким приоритетом.
- `GET /api/tasks?search=text` ищет по `title` и `description`.
- `POST /api/tasks` создает задачу при валидных данных.
- `POST /api/tasks` возвращает ошибку валидации при пустом `title`.
- `GET /api/tasks/{task_id}` возвращает задачу или `404`.
- `PATCH /api/tasks/{task_id}` обновляет только переданные поля.
- `DELETE /api/tasks/{task_id}` удаляет задачу или возвращает `404`.

### AI API

- `POST /api/ai/generate-tasks` возвращает массив предложенных задач.
- `POST /api/ai/split-task` возвращает массив подзадач.
- `POST /api/ai/improve-task` возвращает улучшенную формулировку.
- AI endpoint-ы не требуют передачи API key с frontend.
- AI endpoint-ы имеют предсказуемый JSON-формат ответа.
- Ошибка внешнего AI API превращается в понятный HTTP-ответ.

## 4. Frontend-критерии

- Приложение открывается без ошибок в браузере.
- На пустом списке отображается empty state.
- Во время загрузки отображается loading state.
- При ошибке запроса отображается error state.
- Форма создания задачи валидирует обязательное название.
- Список задач обновляется после создания, редактирования и удаления.
- Фильтры и поиск доступны без перезагрузки страницы.
- Интерфейс остается пригодным на мобильной ширине экрана.
- AI-действия визуально отделены от обычных CRUD-действий.
- AI-предложения не применяются без подтверждения пользователя.
- Базовые frontend-автотесты покрывают empty state, создание задачи и ошибку backend.
- Frontend-тесты используют моки API и не требуют запущенного backend.

## 5. UI/UX-критерии

- Интерфейс соответствует UI/UX-правилам.
- Экран задач не выглядит как landing page или декоративная демо-страница.
- Основной layout остается понятным на desktop и mobile.
- Статусы задач не передаются только цветом.
- Primary action используется ограниченно и не конкурирует с второстепенными действиями.
- У полей формы есть видимые labels.
- Ошибки форм написаны понятным языком и отображаются рядом с соответствующими полями.
- Empty state объясняет, что пусто и что пользователь может сделать дальше.
- Loading state не ломает layout.
- Error state объясняет проблему и дает понятное следующее действие, если оно возможно.
- Destructive-действия требуют подтверждения или очевидного безопасного сценария.
- Ключевые действия имеют стабильные accessible names для автотестов.

## 6. AI-критерии

- AI-запросы идут только через backend.
- Frontend не содержит AI API key.
- Backend читает AI API key из переменной окружения.
- При отсутствии ключа приложение не падает.
- Мок-ответы достаточно реалистичны для демонстрации курса.
- Пользователь контролирует применение AI-предложений.

## 7. Ошибки и пустые состояния

Должны быть обработаны:

- пустой список задач;
- пустой результат фильтрации;
- недоступный backend;
- ошибка создания задачи;
- ошибка обновления задачи;
- ошибка удаления задачи;
- ошибка AI-запроса;
- невалидные значения `status` и `priority`;
- неизвестный `task_id`.

## 8. Минимальные проверки перед финальным ответом агента

Перед завершением каждой разработки агент должен проверить и сообщить:

- какие файлы были изменены;
- какие критерии приемки закрыты;
- какие критерии еще не закрыты;
- проверялось ли соответствие , если задача затрагивала UI;
- какие команды запускались;
- были ли ошибки при проверке;
- не добавлены ли секреты;
- не создано ли лишнее вне текущего этапа.

Минимальные команды будут зависеть от созданного проекта. Ожидаемые типы проверок:

- запуск backend;
- запуск frontend;
- backend-тесты, если уже добавлены;
- frontend-тесты, если уже добавлены;
- frontend build или typecheck, если уже настроены;
- ручная проверка основных сценариев.

## 9. Необязательное для текущего этапа

Следующее не является обязательным для MVP на третьем уроке:

- авторизация;
- роли пользователей;
- Docker-запуск;
- Playwright E2E;
- production-деплой;
- CI/CD;
- сложная система подзадач с деревом зависимостей;
- drag-and-drop доска;
- уведомления;
- календарная интеграция;
- полноценный дизайн-системный UI kit.

Эти пункты можно добавить позже, только если базовый MVP уже работает и покрыт проверками.
