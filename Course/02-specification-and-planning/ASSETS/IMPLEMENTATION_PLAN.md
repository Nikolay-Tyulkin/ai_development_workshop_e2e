# IMPLEMENTATION_PLAN: TaskerAI

## 1. Цель плана

Разбить реализацию MVP на небольшие проверяемые этапы. План предназначен для третьего урока курса, где агент будет писать код итерациями на основе `PROJECT_SPEC.md`, а проверяться по `ACCEPTANCE_CRITERIA.md`.

На втором уроке код не создается.

## 2. Целевая структура проекта

```text
TaskerAI/
  AGENTS.md
  TOOLS.md
  PROJECT_SPEC.md
  IMPLEMENTATION_PLAN.md
  ACCEPTANCE_CRITERIA.md
  README.md
  .env.example

  backend/
    app/
      main.py
      models.py
      schemas.py
      database.py
      routers/
        tasks.py
        ai.py
      services/
        ai_service.py
    tests/
    requirements.txt

  frontend/
    src/
      App.tsx
      main.tsx
      api/
      components/
      styles/
    package.json
    vite.config.ts
    vitest.config.ts
```

Docker-файлы, Playwright, E2E-тесты и расширенная документация добавляются позже. Базовые frontend-автотесты на Vitest/Testing Library входят в MVP третьего урока.

## 3. Этапы реализации

### Этап 1. Подготовить каркас проекта

Цель: создать минимальную структуру `backend` и `frontend`, которая запускается локально.

Задачи:

- создать backend-папку с FastAPI-приложением;
- создать frontend-папку с Vite + React + TypeScript;
- добавить `.env.example` без секретов;
- добавить базовые команды запуска в `README.md` проекта;
- проверить, что backend отвечает на health endpoint;
- проверить, что frontend открывается в браузере.

Проверка:

- backend запускается локально;
- frontend запускается локально;
- секреты не добавлены в код;
- структура не содержит Docker-файлов раньше четвертого урока.

Зависимости: нет.

### Этап 2. Реализовать backend для задач

Цель: создать API задач и хранение данных.

Задачи:

- настроить SQLite;
- описать модель `Task`;
- добавить `parent_id` для вложенных подзадач;
- описать Pydantic-схемы для создания, обновления и ответа;
- реализовать `GET /api/tasks`;
- реализовать `POST /api/tasks`;
- реализовать `GET /api/tasks/{task_id}`;
- реализовать `PATCH /api/tasks/{task_id}`;
- реализовать `DELETE /api/tasks/{task_id}`;
- добавить фильтрацию по `status`, `priority` и `search`.

Проверка:

- API возвращает корректные HTTP-статусы;
- обязательное поле `title` валидируется;
- неизвестный `task_id` возвращает `404`;
- фильтры и поиск работают вместе;
- backend можно проверить через Swagger UI или HTTP-клиент.

Зависимости: этап 1.

### Этап 3. Реализовать базовый frontend задач

Цель: дать пользователю интерфейс для CRUD-операций с задачами.

Задачи:

- создать API-клиент для backend;
- вывести список задач;
- добавить форму создания задачи;
- добавить редактирование задачи;
- добавить удаление задачи;
- добавить смену статуса;
- добавить фильтры по статусу и приоритету;
- добавить поиск;
- добавить loading, error и empty states;
- соблюдать критерии интерфейса из `ACCEPTANCE_CRITERIA.md`;
- сделать интерфейс адаптивным для desktop и mobile;
- настроить Vitest, Testing Library и jsdom;
- добавить тесты для empty state, создания задачи и ошибки backend.

Проверка:

- пользователь может создать задачу из UI;
- пользователь видит созданную задачу в списке;
- пользователь может изменить статус;
- пользователь может отфильтровать и найти задачу;
- пользователь может удалить задачу;
- ошибка backend отображается понятным сообщением;
- UI не использует случайные декоративные стили;
- frontend-тесты проходят без запущенного backend.

Зависимости: этап 2.

### Этап 4. Добавить AI backend endpoint-ы

Цель: подготовить AI-функции через backend без раскрытия секретов на frontend.

Задачи:

- создать `ai_service.py`;
- добавить чтение AI API key из переменной окружения;
- реализовать мок-режим при отсутствии ключа или через отдельную настройку;
- реализовать `POST /api/ai/generate-tasks`;
- реализовать `POST /api/ai/split-task`;
- реализовать `POST /api/ai/improve-task`;
- возвращать структурированные ответы.

Проверка:

- AI endpoint-ы работают без реального ключа в мок-режиме;
- frontend не получает и не хранит AI API key;
- ответы имеют предсказуемую структуру;
- ошибки AI API не ломают весь backend.

Зависимости: этап 2.

### Этап 5. Подключить AI-функции во frontend

Цель: сделать AI-помощника доступным пользователю.

Задачи:

- добавить UI-блок для генерации задач по цели;
- добавить действие "разбить на подзадачи" для выбранной задачи;
- показывать подзадачи как чекбоксы внутри родительской задачи;
- добавить действие "улучшить формулировку";
- позволить пользователю принять или отклонить предложения AI;
- визуально отделить AI-действия от обычных CRUD-действий;
- показывать loading и error states для AI-запросов.

Проверка:

- пользователь может получить предложенные задачи;
- пользователь может добавить выбранные предложения в список;
- пользователь может улучшить текст задачи перед сохранением;
- AI-предложения не применяются без подтверждения пользователя;
- AI-ошибки не блокируют обычную работу с задачами.

Зависимости: этапы 3 и 4.

### Этап 6. Минимальная стабилизация MVP

Цель: подготовить приложение к тестированию и Docker-этапу.

Задачи:

- убрать очевидные дубли и мертвый код;
- проверить соответствие `PROJECT_SPEC.md`;
- проверить соответствие `ACCEPTANCE_CRITERIA.md`;
- проверить запуск базовых frontend-автотестов;
- обновить `README.md` с локальным запуском;
- составить список задач для урока 4.

Проверка:

- основные сценарии выполняются вручную;
- базовые frontend-автотесты проходят;
- приложение можно запустить по инструкции;
- известные ограничения описаны;
- задачи Docker и E2E явно перенесены на урок 4.

Зависимости: этапы 1-5.

## 4. Рекомендуемый порядок задач для агента

1. Создать backend-каркас и health endpoint.
2. Создать frontend-каркас и стартовую страницу.
3. Реализовать модель и API задач.
4. Проверить API вручную.
5. Реализовать список задач во frontend.
6. Добавить создание и редактирование задач.
7. Добавить фильтры, поиск и статусы.
8. Добавить базовые frontend-автотесты без Playwright.
9. Реализовать мок AI endpoint-ы.
10. Подключить AI UI.
11. Провести сверку с критериями приемки.

Каждую задачу нужно давать агенту отдельно или небольшими группами. Не стоит просить сразу "реализуй все приложение".

## 5. Проверки после каждого этапа

После каждого этапа агент должен сообщить:

- какие файлы изменены;
- какие сценарии реализованы;
- какие команды проверки выполнены;
- что не удалось проверить;
- какие риски остались.

Минимальные проверки:

- backend запускается без ошибок;
- frontend собирается или запускается без ошибок;
- API contract соответствует `PROJECT_SPEC.md`;
- frontend проверяется вручную и быстрыми тестами, если этап затрагивал UI;
- секреты не попали в код;
- изменения не выходят за рамки текущего этапа.

## 6. Зависимости

| Этап | Зависит от | Почему |
| --- | --- | --- |
| 1. Каркас | Нет | Нужна основа проекта |
| 2. Backend задач | 1 | Нужен backend-каркас |
| 3. Frontend задач | 2 | UI должен работать с реальным API |
| 4. AI backend | 2 | AI endpoint-ы добавляются в backend |
| 5. AI frontend | 3, 4 | UI должен вызвать готовые AI endpoint-ы |
| 6. Стабилизация | 1-5 | Проверяется собранный MVP |

## 7. Риски и снижение рисков

| Риск | Снижение риска |
| --- | --- |
| Агент начнет слишком большую реализацию | Давать задачи по одному этапу и требовать отчет после каждого этапа |
| AI API окажется недоступен | Сначала реализовать мок-режим |
| Frontend и backend разойдутся по контракту | Держать endpoint-ы из `PROJECT_SPEC.md` источником правды |
| UI станет слишком сложным или случайным | Не добавлять декоративные паттерны без необходимости и сверяться с критериями приемки |
| Подзадачи усложнят модель | Ограничиться одним уровнем `parent_id` и чекбоксами внутри родительской задачи |
