# REVIEW_EXAMPLE: пример ревью MVP после урока 3

## Контекст ревью

Ревью выполняется после реализации MVP приложения "Менеджер задач с ИИ". Цель ревью - не улучшить все сразу, а найти блокеры перед переходом к уроку 4, где появятся Playwright, E2E и Docker. Базовые frontend-автотесты уже должны быть добавлены на уроке 3.

Агент должен смотреть на проект как senior full-stack engineer и не менять файлы без отдельного разрешения.

## Пример промпта

```text
Проведи ревью текущего MVP как senior full-stack engineer.
Ничего не меняй без отдельного разрешения.

Используй PROJECT_SPEC.md, IMPLEMENTATION_PLAN.md и ACCEPTANCE_CRITERIA.md как источники правды.

Проверь:
1. соответствие MVP требованиям;
2. соответствие интерфейса ;
3. критичные баги в backend;
4. критичные баги во frontend;
5. корректность контракта между frontend и backend;
6. безопасную обработку AI API key;
7. работу мок-режима AI;
8. наличие базовых frontend-автотестов без Playwright;
9. отсутствие Docker, Playwright и E2E до урока 4;
10. отсутствие лишних абстракций и большого рефакторинга;
11. актуальность README;
12. что обязательно протестировать на уроке 4.

Верни findings по приоритету: critical, important, minor.
Для каждого finding укажи файл или область, риск и минимальное исправление.
```

## Пример хорошего ответа агента

```text
Critical findings: нет.

Important findings:
1. backend/app/routers/tasks.py - PATCH endpoint принимает пустой JSON и возвращает 200 без изменений.
   Риск: frontend может считать, что задача обновлена, хотя пользователь ничего не поменял.
   Минимальное исправление: вернуть 400, если тело PATCH не содержит ни одного допустимого поля.

2. frontend/src/api/tasks.ts - базовый URL API захардкожен как http://localhost:8000.
   Риск: на уроке 4 Docker и E2E потребуют конфигурацию через переменные окружения.
   Минимальное исправление: использовать VITE_API_BASE_URL с безопасным fallback для локального запуска.

3. backend/app/services/ai_service.py - мок-ответы AI имеют свободный текстовый формат.
   Риск: frontend сложнее стабильно обрабатывать ответы и тестировать сценарии.
   Минимальное исправление: вернуть единый JSON-формат с массивом suggestions.

Minor findings:
1. frontend/src/App.tsx - компонент стал слишком большим.
   Риск: усложнит поддержку, но не блокирует MVP.
   Минимальное исправление: на уроке 5 можно вынести TaskForm и TaskList, сейчас не обязательно.

2. README.md - нет отдельного раздела Known limitations.
   Риск: участнику курса неочевидно, что Docker и E2E будут добавлены позже.
   Минимальное исправление: добавить короткий список ограничений текущего этапа.

Что обязательно проверить на уроке 4:
1. backend CRUD API через pytest;
2. валидацию title, status и priority;
3. мок AI endpoint-ов;
4. frontend unit/component тесты для создания, empty state и ошибок;
5. E2E-сценарий полного пути пользователя через Playwright;
6. запуск backend и frontend через Docker Compose.
```

## Признаки плохого ревью

- агент сразу меняет код без разрешения;
- ревью состоит только из фразы "все хорошо";
- нет приоритета проблем;
- нет ссылок на файлы или области кода;
- предлагается большой рефакторинг вместо минимальных исправлений;
- агент требует добавить Docker, Playwright или E2E до урока 4;
- агент игнорирует отсутствие базовых frontend-автотестов;
- агент игнорирует `` при проверке интерфейса;
- агент игнорирует `ACCEPTANCE_CRITERIA.md`.

## Как исправлять замечания

После ревью не нужно давать агенту команду "исправь все". Лучше исправлять по одному блоку.

Пример:

```text
Исправь только important finding 2 из ревью: вынеси базовый URL API во frontend-конфигурацию через VITE_API_BASE_URL.

Не меняй backend.
Не трогай AI-функции.
Не делай рефакторинг компонентов.

После изменения покажи, какие файлы изменены и как проверить локальный запуск.
```

Такой подход сохраняет контроль над объемом изменений и не превращает стабилизацию MVP в неконтролируемую переработку проекта.
