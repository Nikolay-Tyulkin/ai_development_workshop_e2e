# Урок 3. Разработка приложения по плану

![Идем реализовывать MVP](../../assets/gifs/lesson-3-development.gif)

## Назначение урока

На третьем этапе `TaskerAI` наконец становится рабочим приложением. Агент уже пишет код, но мы не просим его "сделать все сразу": идем короткими итерациями по `IMPLEMENTATION_PLAN.md` и каждый раз сверяемся с `PROJECT_SPEC.md` и `ACCEPTANCE_CRITERIA.md`.

В этом уроке мы учимся:

- выдавать агенту маленькие задачи;
- ограничивать объем изменений на каждой итерации;
- проверять backend, frontend и интеграцию;
- добавлять базовые backend-автотесты для API задач;
- добавлять базовые frontend-автотесты для устойчивой разработки UI;
- добавлять AI-функции через безопасный backend-слой;
- проводить ревью сгенерированного кода перед переходом к E2E и Docker.

Главная цель урока - получить MVP `TaskerAI`, который запускается локально и покрывает основные пользовательские сценарии.

## Результат урока

К концу урока в рабочем проекте должна появиться примерно такая структура:

```text
project-root/
  AGENTS.md
  PROJECT_SPEC.md
  IMPLEMENTATION_PLAN.md
  ACCEPTANCE_CRITERIA.md
  README.md

  backend/

      database.py
      routers/

      App.tsx

```

Docker, Playwright, полноценный набор E2E-автотестов, changelog и release notes оставляем на следующие уроки. Сейчас нам нужны базовые backend-тесты на pytest и легкие frontend-тесты на Vitest и Testing Library, чтобы не ломать основные сценарии во время разработки.

## Шаг 1. Проверить готовность после второго урока

Откройте рабочий проект, в котором лежат документы второго урока.

Минимально должны быть готовы:

- `PROJECT_SPEC.md`;
- `IMPLEMENTATION_PLAN.md`;
- `ACCEPTANCE_CRITERIA.md`;
- агентная среда из первого урока;
- установленный Python;
- установленный Node.js и npm.

Проверочный промпт:

```text
Прочитай PROJECT_SPEC.md, IMPLEMENTATION_PLAN.md и ACCEPTANCE_CRITERIA.md.
Ничего не меняй.

Кратко скажи, готов ли проект к реализации MVP на уроке 3.
Проверь:
1. есть ли все обязательные документы;
2. понятен ли стек backend и frontend;
3. понятны ли критерии интерфейса для frontend;
4. разбит ли план на маленькие этапы;
5. какие команды и зависимости понадобятся для локального запуска.
```

Если агент находит противоречия в документах, сначала исправьте документы минимальными правками. Не начинайте писать код при неясных требованиях.

## Шаг 2. Создать каркас проекта

Первую кодовую задачу держим максимально узкой: только инфраструктурный минимум. Агент не должен сразу реализовывать все приложение.

Промпт:

```text
Используй IMPLEMENTATION_PLAN.md и PROJECT_SPEC.md.

Реализуй только каркас проекта.

Нужно создать:
1. backend на FastAPI с health endpoint;
2. frontend на Vite + React + TypeScript со стартовой страницей;
3. .env.example без секретов;
4. README.md с командами локального запуска.

Не реализуй CRUD задач.
Не реализуй AI-функции.
Не добавляй Docker.
Не добавляй Playwright.
Не добавляй E2E-тесты.

После изменений сообщи:
1. какие файлы созданы;
2. какие команды запуска использовать;
3. какие проверки выполнены;
4. что осталось сделать следующим этапом.
```

Минимальная проверка после шага:

- backend запускается локально;
- health endpoint возвращает успешный ответ;
- frontend открывается локально;
- в код не добавлены секреты;
- Docker-файлы не созданы.

## Шаг 3. Реализовать backend задач

После каркаса поручаем агенту только backend-часть задач. Frontend на этом шаге не трогаем, кроме случаев, когда нужно обновить README с командами проверки.

Промпт:

```text
Используй PROJECT_SPEC.md, IMPLEMENTATION_PLAN.md и ACCEPTANCE_CRITERIA.md.

Реализуй только backend для задач.

Нужно:
1. настроить SQLite;
2. создать модель Task;
3. создать Pydantic-схемы;
4. реализовать endpoint-ы CRUD задач;
5. добавить фильтрацию по status, priority и search;
6. вернуть корректные HTTP-статусы и ошибки валидации;
7. добавить базовые pytest-тесты для API задач;
8. добавить или уточнить команду запуска backend-тестов в README.

Frontend не меняй.
AI endpoint-ы не добавляй.
Docker не добавляй.

После изменений покажи команду запуска backend-тестов и примеры ручной проверки API через Swagger UI или HTTP-запросы.
```

Пример минимальной проверки после шага:

- `POST /api/tasks` создает задачу;
- `GET /api/tasks` возвращает список;
- `PATCH /api/tasks/{task_id}` обновляет задачу;
- `DELETE /api/tasks/{task_id}` удаляет задачу;
- неизвестный `task_id` возвращает `404`;
- пустой `title` не проходит валидацию;
- backend-тесты запускаются одной командой.

## Шаг 4. Реализовать frontend задач

Теперь агент подключает интерфейс к реальному backend API. Здесь важно требовать рабочие пользовательские сценарии, а не просто верстку.

Промпт:

```text
Используй готовый backend API и ACCEPTANCE_CRITERIA.md.

Реализуй frontend для задач.

Нужно:
1. создать API-клиент для backend;
2. вывести список задач;
3. добавить форму создания задачи;
4. добавить редактирование задачи;
5. добавить удаление задачи;
6. добавить смену статуса;
7. добавить фильтры по status и priority;
8. добавить поиск;
9. показать loading, error и empty states;
10. сохранить адаптивность для desktop и mobile;
11. не добавлять случайные декоративные стили;
12. Не агрегируй большое количество функционала на одной странице, если появляются какие-либо настройки или другой домен действий (например создание нового тега\статуса), выноси их в отдельную страницу на сайдбаре.

Backend меняй только если обнаружишь несовместимость контракта, и сначала объясни причину.
AI-функции пока не добавляй.
Docker не добавляй.

После изменений опиши ручной сценарий проверки в браузере.
```

Минимальная проверка после шага:

- задача создается из UI;
- список обновляется после создания;
- задача редактируется;
- статус меняется;
- фильтры и поиск работают;
- задача удаляется;
- ошибка backend отображается пользователю;
- UI соответствует требованиям.

Если базовый вариант фронтенда не устраивает, дополнительным промтом можно добавить правки в таком виде:
```text
Внеси правки в интерфейс frontend, необходимо сделать:
1. Задача должна создавать по кнопке (которая будет в правом верхнем углу), по нажатию должна открываться модалка с формой заполнения
2. Фильтры должны находиться сверху над контейнером со списком задач

После изменений, если есть серьезные изменения в коде\архитектуре\стеке зафиксируй это в ответственных за это документах
```

## Шаг 5. Добавить базовые frontend-автотесты

Перед AI-функциями фиксируем основные сценарии быстрыми тестами. Это не E2E и не Playwright: тесты запускаются внутри frontend-проекта и помогают безопаснее продолжать разработку интерфейса.

Промпт:

```text
Используй готовый frontend задач и ACCEPTANCE_CRITERIA.md.

Добавь базовые frontend-автотесты без Playwright.

Нужно:
1. установить и настроить Vitest, Testing Library и jsdom;
2. добавить npm script для запуска frontend-тестов;
3. покрыть тестами отображение empty state;
4. покрыть тестами создание задачи через UI с моками API;
5. покрыть тестами отображение ошибки backend;
6. не запускать реальные backend-запросы из тестов;
7. не добавлять Playwright и E2E-сценарии.

После изменений сообщи:
1. какие файлы тестов добавлены;
2. какой командой запускать frontend-тесты;
3. какие сценарии покрыты;
```

Минимальная проверка после шага:

- frontend-тесты запускаются одной npm-командой;
- тесты не требуют запущенного backend;
- проверены empty, create и error state;
- Playwright не установлен.

## Шаг 6. Добавить AI backend endpoint-ы

AI-функции должны идти через backend. Frontend не должен видеть и хранить API key.

Промпт:

```text
Используй PROJECT_SPEC.md и ACCEPTANCE_CRITERIA.md.

Реализуй только backend endpoint-ы для AI-функций.

Нужно:
1. создать сервис AI-интеграции;
2. читать AI API key из переменной окружения;
3. добавить мок-режим, который работает без реального ключа;
4. реализовать POST /api/ai/generate-tasks;
5. реализовать POST /api/ai/split-task;
6. реализовать POST /api/ai/improve-task;
7. возвращать структурированные ответы;
8. обрабатывать ошибки без падения backend.

Frontend не меняй.
Секреты не добавляй в код и .env.example.
Docker не добавляй.

После изменений покажи примеры запросов и ответов для мок-режима.
```

Минимальная проверка после шага:

- AI endpoint-ы отвечают без реального API key;
- формат ответа предсказуем;
- ошибки возвращаются контролируемо;
- frontend не содержит секретов.

## Шаг 7. Подключить AI-функции во frontend

На этом шаге пользователь получает AI-помощника, но все предложения AI должны быть подтверждаемыми. Агент не должен автоматически менять задачи без действия пользователя.

Промпт:

```text
Используй готовые backend AI endpoint-ы и ACCEPTANCE_CRITERIA.md.

Подключи AI-функции во frontend.

Нужно:
1. добавить блок генерации задач по описанию цели;
2. позволить пользователю выбрать, какие предложенные задачи добавить;
3. добавить действие разбиения выбранной задачи на подзадачи;
4. добавить действие улучшения формулировки задачи;
5. показывать loading и error states для AI-запросов;
6. визуально отделить AI-действия от обычных CRUD-действий;
7. не применять AI-предложения без подтверждения пользователя;
8. не блокировать обычную работу с задачами при ошибке AI.

Backend меняй только при несовместимости контракта и объясни причину.
Docker не добавляй.
Playwright не добавляй.
E2E-тесты не добавляй.

После изменений опиши ручной сценарий проверки AI-функций.
```

Минимальная проверка после шага:

- пользователь генерирует предложения задач;
- пользователь выбирает предложения и добавляет их в список;
- пользователь разбивает задачу на подзадачи;
- пользователь улучшает формулировку;
- AI-предложения применяются только после подтверждения;
- AI-ошибка не ломает CRUD задач.

Если вариант frontend не устраивает, так же как в прошлый раз, дополнительным промптом можно добавить правки в таком виде:
```text
Внеси правки в интерфейс frontend, необходимо сделать:
1. Генерация задачи по цели должна находиться в модалке "Создать задачу". Цель и ожидаемый результат бери из введенных заголовка и описания, а перед созданием предзаполняй форму. Добавь кнопку "Улучшить с помощью AI" и иконку волшебной палочки.
2. Разбиение задачи и улучшение формулировки добавь кнопками с иконками в карточки задач. Подзадачи должны отображаться чекбоксами внутри задачи, которую разбили, и сохраняться через `parent_id`.
3. Добавь новую страницу "AI история", где будет отображаться история запросов к ИИ, если backend позволяет.

После изменений, если есть серьезные изменения в коде\архитектуре\стеке зафиксируй это в ответственных за это документах
```

## Шаг 8. Провести ревью MVP

Перед переходом к четвертому уроку нужно остановиться и проверить, что агент не вышел за рамки MVP.

Промпт:

```text
Проведи ревью текущего MVP как senior full-stack engineer.
Ничего не меняй без отдельного разрешения.

Проверь:
1. соответствие PROJECT_SPEC.md;
2. соответствие ACCEPTANCE_CRITERIA.md;
3. не появились ли Docker, Playwright, E2E-тесты, changelog или лишняя документация раньше нужного урока;
4. нет ли секретов в коде;
5. нет ли слишком сложных абстракций для учебного MVP;
6. корректно ли разделены backend, frontend и AI-интеграция;
7. покрывают ли backend-автотесты API задач;
8. покрывают ли frontend-автотесты основные UI-сценарии;

Верни findings по приоритету: critical, important, minor через инструмент question в opencode.
Если критичных проблем нет, явно напиши это.
```

Если ревью нашло проблемы, дайте агенту отдельную маленькую задачу на исправление каждого critical или important пункта.

## Критерии готовности урока

Урок можно считать закрытым, если на все пункты ниже получается ответить "да":

- backend запускается локально;
- frontend запускается локально;
- есть API задач с CRUD-операциями;
- задачи сохраняются в SQLite или другом согласованном локальном хранилище;
- frontend работает с реальным backend API;
- frontend соответствует критериям интерфейса;
- пользователь может создать, увидеть, изменить, отфильтровать, найти и удалить задачу;
- AI endpoint-ы работают;
- AI-функции доступны из frontend и не ломают обычную работу с задачами;
- есть базовые backend-автотесты для CRUD задач, фильтров, поиска и ошибок;
- есть базовые frontend-автотесты для empty, create и error state;
- frontend-автотесты запускаются без реального backend;
- секреты не попали в код;
- Docker, Playwright и E2E-тесты не добавлены раньше четвертого урока;
- README проекта содержит команды локального запуска;
- агент провел ревью MVP.
