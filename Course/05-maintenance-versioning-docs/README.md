# Урок 5. Сопровождение, версии и новая фича

![Стабильная версия и новая фича](../../assets/gifs/lesson-5-maintenance.gif)

## Назначение урока

На пятом этапе берем проверенный MVP `TaskerAI` после тестов и Docker-запуска, фиксируем его как первую стабильную версию, а затем проходим полный цикл разработки новой фичи: feature branch, артефакты, реализация, проверка и внесение изменений обратно в основную ветку.

Главная цель урока - научиться сопровождать проект после MVP: работать с SemVer, changelog, git-ветками и документацией фич так, чтобы проект можно было развивать дальше без хаоса.

## Результат урока

К концу урока в рабочем проекте должны появиться или быть обновлены:

```text
project-root/
  CHANGELOG.md
  README.md
  .opencode/
    skills/
      feature-artifacts/
        SKILL.md
  features/
    001-2026-06-05-kanban-board/
      FEATURE_SPEC.md
      IMPLEMENTATION_PLAN.md
      ACCEPTANCE_CRITERIA.md
```

Также должны быть выполнены git-операции:

- MVP зафиксирован как версия `0.1.0`;
- создан коммит первой версии;
- создана feature branch `feature/kanban-board`;
- фича "Канбан-доска" разработана в отдельной ветке;
- фича внесена обратно в основную ветку;
- changelog обновлен версией `0.2.0` после добавления фичи.

## Правило организации фич

Каждая новая фича получает отдельную папку в `features/`:

```text
features/
  NNN-YYYY-MM-DD-feature-slug/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md
```

Где:

- `NNN` - порядковый номер фичи с ведущими нулями;
- `YYYY-MM-DD` - дата создания артефактов;
- `feature-slug` - короткое название фичи на английском в kebab-case.

Для этого урока используем:

```text
features/
  001-2026-06-05-kanban-board/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md
```

Три документа нужны для разделения ответственности:

- `FEATURE_SPEC.md` описывает, что именно нужно сделать и зачем;
- `IMPLEMENTATION_PLAN.md` описывает, как реализовать фичу маленькими шагами;
- `ACCEPTANCE_CRITERIA.md` фиксирует, по каким признакам фича считается готовой.

Чтобы не писать эту структуру каждый раз вручную, можно добавить project skill `feature-artifacts`. Пример готового skill лежит в материалах урока:

```text
Course/05-maintenance-versioning-docs/ASSETS/.opencode/skills/feature-artifacts/SKILL.md
```

В рабочем проекте он должен лежать здесь:

```text
.opencode/
  skills/
    feature-artifacts/
      SKILL.md
```

Промпт для создания skill в рабочем проекте:

```text
Создай project skill для оформления артефактов новой фичи.

Название skill:
feature-artifacts

Путь:
.opencode/skills/feature-artifacts/SKILL.md

Skill должен срабатывать, когда нужно создать новую продуктовую фичу и до реализации подготовить папку:

features/
  NNN-YYYY-MM-DD-feature-slug/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md

Требования к skill:
1. используй корректный frontmatter для opencode skill;
2. name должен быть feature-artifacts;
3. description должен явно говорить, когда использовать skill;
4. опиши правило именования папки фичи;
5. опиши обязательные разделы FEATURE_SPEC.md;
6. опиши обязательные разделы IMPLEMENTATION_PLAN.md;
7. опиши обязательные разделы ACCEPTANCE_CRITERIA.md;
8. запрети менять код приложения при создании артефактов;
9. добавь правило задавать уточняющий вопрос, если границы фичи неясны.

Код приложения не меняй. Если есть уточняющие вопросы, задавай через инструмент question.
```

После добавления или изменения skill перезапустите opencode, чтобы он загрузил новый файл конфигурации.

## Шаг 1. Проверить состояние проекта, создать changelog и закоммитить первую версию

Сначала фиксируем результат уроков 1-4 как стабильную базу. Новую фичу нельзя начинать поверх непонятного состояния проекта.

Минимально должны быть готовы:

- рабочий backend;
- рабочий frontend;
- backend-тесты;
- frontend-тесты;
- Playwright E2E-тесты;
- Docker-запуск;
- README с актуальными командами;
- `.env.example` без секретов.

Первая версия учебного MVP - `0.1.0`.

Промпт:

```text
Проверь текущее состояние проекта после MVP.

Сначала ничего не меняй.

Нужно проверить:
1. git status;
2. текущую ветку;
3. актуальность README и команд запуска;
4. backend-тесты;
5. frontend-тесты;
6. Playwright E2E-тесты;
7. Docker build и Docker-запуск, если Docker доступен;
8. отсутствие секретов в коде, .env.example, Dockerfile и docker-compose.yml;
9. остаточные риски перед первой версией.

Если критичных блокеров нет:
1. создай CHANGELOG.md;
2. добавь первую версию 0.1.0 по SemVer;
3. опиши, что вошло в MVP;
4. добавь known issues, если они есть;
5. сделай git commit всех изменений.

Commit message:
Release 0.1.0 MVP

Не используй force push.
Не используй git reset --hard.
Не добавляй реальные секреты.
```

Пример `CHANGELOG.md`:

```md
# Changelog

Все заметные изменения проекта фиксируются в этом файле.

Формат основан на Keep a Changelog, версии следуют SemVer.

## 0.1.0 - 2026-06-05

### Added
- MVP приложения TaskerAI.
- Backend API для задач.
- Frontend-интерфейс для работы с задачами.
- AI-функции в мок-режиме.
- Backend- и frontend-автотесты.
- Playwright E2E-сценарии.
- Docker Compose запуск.

### Known Issues
- Реальная AI-интеграция не включена в учебный MVP.
```

Минимальная проверка после шага:

- `CHANGELOG.md` создан;
- версия `0.1.0` описывает текущее состояние MVP;
- рабочее дерево чистое после коммита;
- последним коммитом является `Release 0.1.0 MVP`.

## Шаг 2. Создать новую ветку под фичу

Теперь начинаем разработку новой фичи отдельно от стабильной версии.

Фича урока: канбан-доска как альтернативное представление тех же задач, которые уже отображаются списком.

Название ветки:

```text
feature/kanban-board
```

Промпт:

```text
Создай новую feature branch для разработки канбан-доски.

Название ветки:
feature/kanban-board

Перед созданием ветки проверь:
1. что рабочее дерево чистое;
2. что текущая ветка содержит коммит Release 0.1.0 MVP;
3. что нет незакоммиченных секретов или временных файлов.

После создания ветки сообщи:
1. текущую ветку;
2. последний коммит;
3. что будет следующим шагом.

Не делай изменений в коде приложения на этом шаге.
```

Минимальная проверка после шага:

- текущая ветка - `feature/kanban-board`;
- рабочее дерево чистое;
- код приложения не изменен.

## Шаг 3. Создать артефакты новой фичи

Перед кодом фиксируем требования, план и критерии приемки. Это защищает от ситуации, когда агент сразу начинает менять UI без понятной границы задачи.

Если в проект добавлен skill `feature-artifacts`, используйте его на этом шаге. Если skill еще не добавлен, создайте документы вручную по структуре ниже или перенесите пример из `ASSETS`.

Структура артефактов:

```text
features/
  001-2026-06-05-kanban-board/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md
```

Промпт:

```text
Создай артефакты для новой фичи "Канбан-доска".

Нужно организовать документы в таком виде:

features/
  001-2026-06-05-kanban-board/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md

Фича:
добавить канбан-доску как альтернативное представление тех же задач, которые уже есть в списке.

Требования к FEATURE_SPEC.md:
1. описать цель фичи;
2. описать пользовательские сценарии;
3. зафиксировать, что используется существующая сущность Task;
4. зафиксировать, что отдельная сущность KanbanTask не создается;
5. описать переключение между list view и board view;
6. описать, что не входит в фичу.

Требования к IMPLEMENTATION_PLAN.md:
1. разбить разработку на маленькие шаги;
2. отдельно описать frontend-изменения;
3. отдельно описать backend-изменения, если они нужны;
4. описать тесты;
5. описать проверки перед merge.

Требования к ACCEPTANCE_CRITERIA.md:
1. пользователь видит канбан-доску;
2. задачи распределены по колонкам статусов;
3. пользователь может переключаться между списком и доской;
4. смена статуса из доски обновляет ту же задачу;
5. существующий список задач не сломан;
6. тесты проходят;
7. Docker-запуск не сломан.

Код приложения пока не меняй.
```

Минимальная проверка после шага:

- создана папка `features/001-2026-06-05-kanban-board/`;
- в ней есть три обязательных документа;
- документы не противоречат текущему MVP;
- код приложения еще не изменен.

## Шаг 4. Разработать фичу

Теперь агент реализует канбан-доску по документам фичи. Важно не создавать вторую модель задач: доска должна быть только другим представлением тех же данных.

Минимальный объем фичи:

- переключатель между списком и доской;
- колонки по существующим статусам задач;
- отображение задач в колонках;
- смена статуса задачи из доски;
- сохранение существующего списка задач;
- тесты на новое поведение;
- обновление README только при изменении пользовательских сценариев или команд.

Drag-and-drop можно оставить за рамками первой версии фичи. Для учебного проекта достаточно надежной смены статуса через кнопку или select внутри карточки.

Промпт:

```text
Разработай фичу "Канбан-доска" по документам из features/001-2026-06-05-kanban-board.

Нужно прочитать FEATURE_SPEC.md, IMPLEMENTATION_PLAN.md и ACCEPTANCE_CRITERIA.md;


После изменений выполни релевантные проверки и верни:
1. список измененных файлов;
2. команды, которые были выполнены;
3. какие критерии приемки закрыты;
4. какие риски остались.
```

Минимальная проверка после шага:

- список задач работает как раньше;
- канбан-доска показывает те же задачи;
- смена статуса из доски сохраняется;
- тесты проходят;
- README не содержит устаревших команд;
- нет секретов.

## Шаг 5. Внести фичу в основную ветку

Финальный шаг - завершить feature workflow. Сначала фиксируем изменения в feature branch, потом вносим их в основную ветку.

Для учебного проекта достаточно локального merge. Если проект ведется на GitHub, этот шаг можно заменить pull request-ом.

Промпт:

```text
Подготовь внесение фичи "Канбан-доска" в основную ветку.

Нужно:
1. проверить git status;
2. проверить текущую ветку;
3. проверить, что мы на feature/kanban-board;
4. запустить релевантные тесты;
5. проверить Docker-запуск, если Docker доступен;
6. сделать commit фичи в feature branch;
7. переключиться на main;
8. влить feature/kanban-board;
9. обновить CHANGELOG.md версией 0.2.0;
10. сделать финальную проверку;
11. показать git log --oneline -5.

Commit message для фичи:
Add kanban board feature

Версия после merge:
0.2.0

Не используй force push.
Не используй git reset --hard.
Не удаляй feature branch без отдельного разрешения.
Не добавляй реальные секреты.
```

Пример записи в `CHANGELOG.md` после merge:

```md
## 0.2.0 - 2026-06-05

### Added
- Канбан-доска как альтернативное представление задач.
- Переключение между списком и доской.
- Распределение задач по колонкам статусов.
- Смена статуса задачи из канбан-представления.
```

Минимальная проверка после шага:

- фича закоммичена в `feature/kanban-board`;
- изменения внесены в `main`;
- `CHANGELOG.md` содержит версию `0.2.0`;
- тесты проходят после merge;
- `git log --oneline -5` показывает понятную историю;
- feature branch не удалена без явного решения.

## Критерии готовности урока

Урок можно считать закрытым, если на все пункты ниже получается ответить "да":

- первая версия MVP зафиксирована как `0.1.0`;
- создан `CHANGELOG.md`;
- сделан коммит `Release 0.1.0 MVP`;
- создана ветка `feature/kanban-board`;
- артефакты фичи лежат в `features/001-2026-06-05-kanban-board/`;
- у фичи есть `FEATURE_SPEC.md`, `IMPLEMENTATION_PLAN.md` и `ACCEPTANCE_CRITERIA.md`;
- канбан-доска использует существующие задачи;
- отдельная сущность `KanbanTask` не создана;
- пользователь может переключаться между списком и доской;
- смена статуса из доски работает;
- существующий список задач не сломан;
- тесты проходят;
- Docker-запуск не сломан;
- фича внесена в основную ветку;
- changelog обновлен версией `0.2.0`.

## Итог урока

После пятого урока проект перестает быть просто учебным MVP и получает базовый процесс сопровождения: версии по SemVer, changelog, feature branch workflow, отдельные артефакты для новой фичи и контролируемое внесение изменений в основную ветку.
