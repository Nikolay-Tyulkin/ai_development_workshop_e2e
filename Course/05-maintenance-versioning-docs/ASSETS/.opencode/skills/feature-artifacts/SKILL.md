## Что делать

Создать артефакты новой фичи до начала изменений в коде приложения.

## Структура

Каждая фича должна жить в отдельной папке:

```text
features/
  NNN-YYYY-MM-DD-feature-slug/
    FEATURE_SPEC.md
    IMPLEMENTATION_PLAN.md
    ACCEPTANCE_CRITERIA.md
```

Где:

- `NNN` - порядковый номер фичи с ведущими нулями;
- `YYYY-MM-DD` - дата создания артефактов;
- `feature-slug` - короткое название фичи на английском в kebab-case.

## Обязательный результат

Создай три документа.

`FEATURE_SPEC.md` должен включать:

- цель фичи;
- пользовательские сценарии;
- затронутые существующие сущности и экраны;
- что должно измениться для пользователя;
- что не входит в фичу;
- риски, допущения и открытые вопросы.

`IMPLEMENTATION_PLAN.md` должен включать:

- этапы реализации маленькими шагами;
- предполагаемые frontend-изменения;
- предполагаемые backend-изменения, если они нужны;
- изменения данных или миграции, если они нужны;
- тесты и проверки;
- зависимости и порядок выполнения;
- решения, которые требуют подтверждения пользователя.

`ACCEPTANCE_CRITERIA.md` должен включать:

- проверяемые пользовательские критерии;
- критерии для существующего поведения, которое нельзя сломать;
- тестовые сценарии;
- критерии документации;
- критерии безопасности и отсутствия секретов;
- критерии готовности к merge.

## Правила

- Не меняй код приложения при создании артефактов фичи.
- Не создавай новую сущность, если фича может использовать существующую модель данных.
- Не смешивай несколько независимых фич в одной папке.
- Если номер следующей фичи неочевиден, посмотри существующие папки в `features/`.
- Если дата не задана пользователем, используй текущую дату в формате `YYYY-MM-DD`.
- Если границы фичи неясны, задай короткий уточняющий вопрос.
- После создания артефактов сообщи путь к папке фичи и кратко перечисли, что зафиксировано.
