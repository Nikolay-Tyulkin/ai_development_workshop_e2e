# TESTING_PLAN: урок 4

## 1. Назначение файла

Этот файл фиксирует, какие проверки нужны для учебного MVP `TaskerAI` после четвертого урока. Его можно использовать как чеклист или как шаблон для рабочего `TESTING_PLAN.md` в проекте.

Главный принцип: каждый уровень тестов проверяет свой тип риска. Быстрые frontend-тесты проверяют UI-компоненты с моками, backend-тесты проверяют API и бизнес-правила, Playwright проверяет реальные пользовательские сценарии через браузер.

## 2. Что уже должно быть после урока 3

- backend запускается локально;
- frontend запускается локально;
- CRUD задач работает через API и UI;
- AI endpoint-ы работают в мок-режиме без реального ключа;
- есть базовые frontend-тесты на Vitest и Testing Library;
- Playwright и Docker еще не обязательны.

## 3. Быстрые frontend-тесты

Эти тесты должны остаться из урока 3 и не заменяются Playwright.

Минимальные сценарии:

- отображение empty state;
- создание задачи через UI с моками API;
- отображение ошибки backend;
- базовая проверка формы создания или редактирования, если она вынесена в отдельный компонент.

Ожидаемая команда:

```powershell
cd frontend
npm test
```

Linux/macOS:

```bash
cd frontend
npm test
```

Если в проекте используется другое имя script, зафиксируйте фактическую команду в README.

## 4. Backend API-тесты

Минимальные сценарии для задач:

- `POST /api/tasks` создает задачу;
- `GET /api/tasks` возвращает список;
- `GET /api/tasks/{task_id}` возвращает одну задачу;
- `PATCH /api/tasks/{task_id}` обновляет задачу;
- `DELETE /api/tasks/{task_id}` удаляет задачу;
- неизвестный `task_id` возвращает `404`;
- пустой `title` возвращает ошибку валидации;
- фильтр по `status` работает;
- фильтр по `priority` работает;
- `search` ищет по названию или описанию в соответствии со спецификацией.

Минимальные сценарии для AI:

- `POST /api/ai/generate-tasks` работает без реального API key;
- `POST /api/ai/split-task` возвращает структурированный список вложенных подзадач;
- `POST /api/ai/improve-task` возвращает улучшенную формулировку;
- ошибки AI возвращаются контролируемо и не раскрывают секреты.

Ожидаемая команда:

```powershell
cd backend
pytest
```

Linux/macOS:

```bash
cd backend
pytest
```

Если backend запускается иначе, README должен содержать фактическую команду.

## 5. Playwright E2E-тесты

E2E-тесты проверяют поведение приложения в браузере. Они не должны подменять все unit и API-тесты.

Минимальные сценарии:

- приложение открывается;
- пустой список задач отображается корректно;
- пользователь создает задачу;
- пользователь редактирует задачу;
- пользователь меняет статус задачи;
- пользователь фильтрует задачи по статусу;
- пользователь фильтрует задачи по приоритету;
- пользователь ищет задачу;
- пользователь удаляет задачу;
- пользователь генерирует предложения задач через AI в мок-режиме;
- пользователь выбирает AI-предложения перед добавлением;
- пользователь улучшает формулировку задачи;
- пользователь разбивает задачу на вложенные подзадачи;
- ошибка AI не ломает обычные CRUD-действия.

Ожидаемая команда:

```powershell
cd frontend
npm run test:e2e
```

Linux/macOS:

```bash
cd frontend
npm run test:e2e
```

Для локального запуска E2E обычно должны быть подняты backend и frontend. Если `playwright.config.ts` сам запускает dev server, это нужно указать в README.

## 6. Ручные проверки

Ручно стоит проверить:

- адаптивность интерфейса на desktop и mobile;
- понятность loading, error и empty states;
- отсутствие секретов в `.env.example`, Dockerfile-ах и тестах;
- корректность команд README;
- запуск через Docker в чистом окружении.

## 7. Что не обязательно для учебного MVP

На четвертом уроке не требуется:

- полноценная CI/CD-система;
- нагрузочное тестирование;
- тестирование во всех браузерах и устройствах;
- production-grade observability;
- реальный AI API key в тестовом прогоне;
- сложная миграционная система, если проект использует учебный SQLite.

## 8. Итоговый чеклист

- `npm test` или аналогичная команда frontend-тестов проходит;
- `pytest` или аналогичная команда backend-тестов проходит;
- `npm run test:e2e` или аналогичная команда Playwright проходит;
- E2E не требует ручной подготовки данных;
- AI проверяется только в мок-режиме;
- Docker build проходит;
- приложение запускается через `docker compose up`;
- README содержит фактические команды.
