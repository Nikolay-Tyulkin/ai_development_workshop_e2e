# Урок 4. Проверка, тестирование и Docker

![Проверяем и ломаем аккуратно](../../assets/gifs/lesson-4-testing-docker.gif)

## Назначение урока

На четвертом этапе берем MVP `TaskerAI` после разработки и доводим его до состояния, которое можно нормально проверить и запустить в контейнерах. Здесь расширяем backend-тесты, добавляем Playwright, E2E-сценарии и Docker-запуск.

Важная граница: базовые backend-тесты на pytest и frontend-автотесты на Vitest и Testing Library уже появились в уроке 3. Здесь мы не начинаем тестирование с нуля, а добавляем следующий слой проверок: AI endpoint-ы в pytest, E2E через Playwright, AI в мок-режиме и запуск всего приложения через Docker.

Главная цель урока - получить приложение, которое можно проверить одной понятной последовательностью команд и запустить в воспроизводимом контейнерном окружении.

## Результат урока

К концу урока в рабочем проекте должна появиться такая структура:

```text
project-root/
  README.md
  .env.example
  docker-compose.yml

  backend/
    Dockerfile
    requirements.txt
    tests/
      test_tasks_api.py
      test_ai_api.py

  frontend/
    Dockerfile
    package.json
    playwright.config.ts
    e2e/
      app.spec.ts
      tasks.spec.ts
      ai.spec.ts
```

Точная структура может отличаться от примера, если проект на третьем уроке был реализован немного иначе. Важно, чтобы были выполнены четыре результата:

- быстрые тесты из урока 3 сохранены и проходят;
- backend-тесты покрывают API задач и AI endpoint-ы;
- E2E-сценарии запускаются через Playwright отдельной командой;
- приложение запускается через `docker compose up`.

## Шаг 1. Проверить стартовое состояние

Минимально должны быть готовы:

- рабочий backend;
- рабочий frontend;
- базовые backend-автотесты для API задач;
- базовые frontend-автотесты без Playwright;
- README с командами локального запуска;
- AI endpoint-ы в мок-режиме;
- список пользовательских сценариев, которые нужно покрыть на уроке 4.

Проверочный промпт:

```text
Проверь готовность проекта.
Ничего не меняй.

Проверь:
1. запускаются ли backend и frontend по README;
2. проходят ли быстрые frontend-тесты из урока 3;
3. проходят ли базовые backend-тесты из урока 3 и какой командой они запускаются;
4. какие пользовательские сценарии нужно покрыть E2E;
5. работают ли AI endpoint-ы без реального API key;
6. нет ли Playwright и Docker, добавленных раньше урока 4;
7. нет ли блокеров перед установкой Playwright и Docker-настройкой.

Верни краткий отчет: ready, blockers, recommended next tasks.
```

Если агент находит блокеры, исправьте их маленькими задачами до установки Playwright и Docker.

## Шаг 2. Составить план тестирования

Перед E2E-тестами фиксируем, что проверяется на каком уровне. Не нужно прогонять один и тот же сценарий всеми видами тестов без причины.

Промпт:

```text
Составь TESTING_PLAN.md для текущего MVP.

Нужно описать:
1. быстрые frontend-тесты, которые уже есть;
2. backend API-тесты, которые нужны для задач;
3. backend API-тесты, которые нужны для AI endpoint-ов;
4. E2E-сценарии Playwright;
5. ручные проверки, которые пока не автоматизируем;
6. команды запуска всех проверок;
7. что не нужно тестировать в учебном MVP.

Не меняй код приложения.
Создай или обнови только TESTING_PLAN.md, а также добавь инструкции по его использованию или внесению изменений в необходимые скиллы и агенты, а также другие спецификации по необходимости.
```

Минимальная проверка после шага:

- есть понятный список E2E-сценариев;
- AI-функции проверяются в мок-режиме;
- команды тестов не требуют реальных секретов;
- план не требует сложной CI/CD-настройки.

## Шаг 3. Расширить backend-тесты

На четвертом уроке базовые тесты API задач уже должны быть готовы. Здесь расширяем покрытие: добавляем AI endpoint-ы, пограничные сценарии и безопасную тестовую конфигурацию, чтобы проверить backend отдельно от браузерных E2E-сценариев.

Промпт:

```text
Расширь backend-тесты для MVP.

Нужно:
1. сохранить и запустить базовые тесты API;
2. при необходимости добавить недостающие проверки фильтрации по status, priority и search;
3. при необходимости добавить недостающие проверки 404 и ошибки валидации для пустого title;
4. покрыть AI endpoint-ы в мок-режиме;
5. убедиться, что тесты не требуют реального AI API key;
6. добавить или уточнить команду запуска backend-тестов в README.

Frontend не меняй.
Playwright не добавляй в этой задаче.
Docker не добавляй в этой задаче.
```

Минимальная проверка после шага:

- backend-тесты запускаются одной командой;
- тесты используют изолированное тестовое хранилище или безопасную тестовую конфигурацию;
- AI endpoint-ы проходят без реальных затрат на API;
- README содержит фактическую команду запуска.

## Шаг 4. Установить Playwright

Playwright устанавливается только на четвертом уроке, когда MVP уже работает и есть быстрые frontend-тесты. Установку лучше поручить агенту отдельной маленькой задачей.

Промпт:

```text
Установи Playwright для frontend-проекта.

Нужно:
1. добавить Playwright как dev dependency внутри frontend;
2. установить браузеры Playwright;
3. добавить npm script для запуска E2E-тестов;
4. создать минимальную конфигурацию Playwright;
5. добавить один smoke E2E-тест, который открывает приложение;
6. не переписывать существующие Vitest/Testing Library тесты;
7. не добавлять Docker в этой задаче.

После изменений сообщи:
1. какие команды установки и проверки выполнены;
2. какие файлы добавлены;
3. как запустить E2E-тесты локально;
4. что осталось покрыть следующими E2E-сценариями.
```

Минимальная проверка после шага:

- Playwright установлен внутри frontend-проекта;
- E2E-тесты запускаются отдельной командой;
- быстрые frontend-тесты из урока 3 сохранены;
- Docker остается отдельным следующим блоком урока 4.

## Шаг 5. Добавить E2E-сценарии задач

После smoke-теста можно покрыть основные пользовательские сценарии. Тесты должны проверять поведение пользователя, а не внутреннюю структуру React-компонентов.

Промпт:

```text
Добавь Playwright E2E-сценарии для задач.

Нужно покрыть тесты из TESTING_PLAN.md для e2e:
1. открытие приложения;
2. отображение пустого состояния;
3. создание задачи;
4. редактирование задачи;
5. смену статуса;
6. фильтр по статусу;
7. фильтр по приоритету;
8. поиск;
9. удаление задачи;
10. состояние ошибки backend, если его можно надежно смоделировать.

Требования:
1. тесты должны запускаться отдельной npm-командой;
2. тесты не должны зависеть от ручной подготовки данных;
3. если нужно очищать данные перед тестом и после, сделай это явно и безопасно;
4. не трогай Vitest/Testing Library тесты без необходимости.
```

Минимальная проверка после шага:

- E2E-тесты проходят при локально запущенных backend и frontend;
- сценарии не зависят от случайного порядка задач;
- тесты не оставляют проект в непредсказуемом состоянии;
- команда запуска описана в README.

## Шаг 6. Проверить AI-функции через E2E

AI-функции на учебном проекте проверяются без реального API key. Цель E2E-проверок - убедиться, что frontend вызывает backend, показывает предложения и применяет их только после подтверждения пользователя.

Промпт:

```text
Добавь E2E-проверки AI-функций в мок-режиме.

Нужно покрыть:
1. генерацию предложений задач по цели;
2. выбор предложений перед добавлением;
3. добавление выбранных предложений в список задач;
4. улучшение формулировки задачи;
5. разбиение задачи на вложенные подзадачи;
6. ошибку AI endpoint-а, если ее можно надежно смоделировать.

Ограничения:
1. не использовать реальный AI API key;
2. не записывать секреты в тесты;
3. не применять AI-предложения без действия пользователя;
4. не ломать обычные CRUD-сценарии при ошибке AI.
```

Минимальная проверка после шага:

- AI E2E-тесты проходят в мок-режиме;
- тесты не требуют сетевых запросов к внешнему AI API;
- предложения AI подтверждаются пользователем;
- ошибки AI не блокируют обычную работу задач.

## Шаг 7. Добавить Docker-запуск

Docker добавляется после тестов, чтобы контейнеризировать уже понятное приложение. Для учебного проекта достаточно простого `docker-compose.yml` с backend, frontend и, если нужно, базой данных.

Промпт:

```text
Добавь Docker-запуск для приложения.

Нужно:
1. создать Dockerfile для backend;
2. создать Dockerfile для frontend;
3. создать docker-compose.yml в корне проекта;
4. настроить переменные окружения через .env.example без секретов;
5. убедиться, что frontend обращается к backend по корректному URL внутри Docker;
6. если используется SQLite, настроить безопасный volume в корень проекта ./data;
7. обновить README с командами docker compose build, up и down и инструкцией по настройке ENV.

Не меняй бизнес-логику приложения.
Не добавляй реальные секреты.
```

Минимальная проверка после шага:

- `docker compose build` проходит;
- `docker compose up` запускает backend и frontend;
- приложение открывается в браузере;
- frontend видит backend;
- секреты не попали в Dockerfile, compose или `.env.example`.

## Шаг 8. Провести приемочную проверку

Финальный шаг урока - проверить проект целиком и зафиксировать команды.

Промпт:

```text
Проведи приемочную проверку.
Ничего не меняй без отдельного разрешения.

Проверь:
1. быстрые frontend-тесты;
2. backend-тесты;
3. Playwright E2E-тесты;
4. Docker build;
5. Docker-запуск приложения;
6. отсутствие секретов в коде и конфигурации;
7. соответствие TESTING_PLAN.md;
8. соответствие ACCEPTANCE_CRITERIA.md.

Верни findings по приоритету: critical, important, minor, используй для этого инструмент question.
Если критичных проблем нет, явно напиши это.
Отдельно перечисли команды, которые были выполнены.
```

Если ревью нашло critical или important проблемы, исправляйте их отдельными маленькими задачами. Не смешивайте исправления тестов, Docker и UI в одном большом запросе.

## Критерии готовности урока

Урок можно считать закрытым, если на все пункты ниже получается ответить "да":

- быстрые frontend-тесты из урока 3 сохранены и проходят;
- backend API задач покрыт тестами;
- AI endpoint-ы покрыты тестами в мок-режиме;
- Playwright установлен на уроке 4, а не раньше;
- есть smoke E2E-тест открытия приложения;
- E2E покрывает создание, редактирование, фильтрацию, поиск и удаление задач;
- E2E покрывает AI-функции без реального API key;
- тесты не хранят секреты;
- README содержит команды запуска всех проверок;
- есть `Dockerfile` для backend;
- есть `Dockerfile` для frontend;
- есть `docker-compose.yml`;
- приложение запускается через `docker compose up`;
- frontend в Docker обращается к backend корректно;
- `.env.example` содержит только безопасные примерные значения;
- агент провел приемочную проверку и перечислил остаточные риски.
